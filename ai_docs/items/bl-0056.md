## Acceptance

- [ ] Every workspace-scoped tool with no path parameter accepts an optional absolute `root_path` (already in `PATH_PARAMS`) that selects its workspace. At HEAD `f2d6074` these are `search_symbols`, `project_search`, `autoimport_search`, `create_type_stubs`, `test_impact_select`, `fix_module_names`, `list_environments`, `restart_server`, `undo_refactoring`, `redo_refactoring`, `get_refactoring_history`, `begin_change_stack`, `commit_change_stack` and `rollback_change_stack`. Re-derive the list when implementing. `refactor_transaction` needs no new parameter: its schema requires steps, and each step's `file_path` resolves it (`_transaction_step_paths`).
- [ ] `diff_preview` is workspace-free: the boundary skips backend resolution for it and the tool drops its discarded `get_current_backends()` call (`tool_registry.py:1522`), because `_resolve_backends` never reads `edits` and the diff builder only reads the files the edits name. A path-less `diff_preview` succeeds with zero live roots and no CLI root (today it raises "No workspace backends available") and with two live roots (where the coded error below would otherwise reject it). Test both.
- [ ] With no path argument, `_resolve_backends` never silently picks a workspace. It raises a coded `AMBIGUOUS_WORKSPACE` error naming the live roots and the `root_path` parameter when several workspaces are live, or when the only candidate is the CLI pre-warm root that no path-bearing call has selected. This applies to reading and mutating tools alike (`fix_module_names` with `apply=true`, undo/redo, the change-stack tools).
- [ ] `tests/unit/test_error_boundary.py:133-160` currently pins the silent fallback (`test_resolve_backends_no_path_uses_most_recent`, `test_resolve_backends_cli_fallback_when_no_recent`). Replace them with red-first tests: two live roots plus a path-less call → coded error; only the pre-warm root plus a path-less call → coded error; `root_path` selects the named workspace.
- [ ] At least one `root_path` test drives a real `WorkspaceRegistry` (only its backend constructors patched, as the registry unit tests' `get_backends` tests do), not the MagicMock registry: `root_path=<unregistered repo root>` selects that root, and `root_path=<primary>/.worktrees/x` with the primary known selects the worktree root. Both need `bl-0055`'s directory-as-own-root walk, hence the dependency.
- [ ] The contract suite asserts `root_path` on the input schema of each listed tool.
- [ ] `ai_docs/runtime.md:66` and `docs/setup.md:88-91` say the positional pre-warm root is for single-project registrations only, and that user-scope multi-repo registrations omit it.

## Evidence

- `tool_runtime.py:167-173`: with no path argument, `_resolve_backends` returns `registry.get_most_recent()`, else initializes the CLI root. `server.py:80-83` eagerly initializes the CLI root at lifespan start, so until a path-bearing call runs, that fallback is the pre-warmed workspace.
- `fix_module_names` (`tool_registry.py:1234`) takes only `apply`; called path-less from another repo with `apply=true` it renames modules in whichever workspace is most recent.
- An AST scan of `tool_registry.py` at HEAD `f2d6074` found 16 `ctx`-taking tools with no path parameter (the 14 above plus `diff_preview` and `refactor_transaction`).
- `diff_preview` (`tool_registry.py:1517-1525`) calls `get_current_backends()` and discards the result. A probe at `f2d6074` (cold review, 2026-09-28) dispatched it through `tool_error_boundary` with a real empty `WorkspaceRegistry` and no CLI root: it raised `RuntimeError: No workspace backends available`.
- Source: 2026-09-27 15-day session retrospective, canonical issue `jedi-workspace-root-misresolution`. One observed path-less probe from a C# repo was answered from the pre-warmed Jedi-Py-MCP workspace (returned `[]`).
