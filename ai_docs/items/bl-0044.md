# bl-0044 — Stop Rope AutoImport pre-warm from spawning a CPU-wide process pool that orphans

**row:** `bl-0044` · **pri:** `High` · **size:** `S`

## Anchors

- `src/python_refactor_mcp/backends/rope_backend.py` (`RopeBackend.initialize` lines 243-258: `autoimport.generate_cache()` pre-warm)
- `tests/unit/test_rope_backend.py` (regression: initialize must not start a process pool)

## Root cause

| Fact | Where |
|---|---|
| `RopeBackend.initialize` calls `AutoImport(...).generate_cache()` synchronously at startup. | `rope_backend.py:247-248` |
| Rope's `generate_cache` runs `with ProcessPoolExecutor() as executor:` with default `max_workers` = CPU count (24 on this machine). | `.venv/Lib/site-packages/rope/contrib/autoimport/sqlite.py:394` (rope 1.14.0) |
| Every Claude Code session starts 2 servers (`python-refactor` + `python-analysis`), so each session start forks ~48 `multiprocessing.spawn` workers. | `~/.claude.json` user-scope registration |
| On Windows, a server killed before the pool drains (session closed, client restart, stdio EOF) leaves its spawn workers running with a dead parent. Nothing reaps them. | observed |

## Acceptance

- [ ] Startup no longer runs a `ProcessPoolExecutor` pre-warm. Pick one: build the cache lazily on the first `autoimport_search`, in-process/single-worker (for example `generate_cache` over a bounded resource set, or a thread instead of processes), or skip the pre-warm for `PYTHON_REFACTOR_MCP_TOOL_PROFILE=analysis`, which does not need it. Justify the choice in the PR.
- [ ] If any process pool remains, give it a bounded `max_workers` and shut it down on server exit and stdio EOF, so a killed server leaves no `spawn_main` children.
- [ ] Regression test: `RopeBackend.initialize()` spawns no child processes (for example, patch `concurrent.futures.ProcessPoolExecutor` to raise, or assert no pool construction), and `autoimport_search` still returns results.
- [ ] `just ci` passes.

## Evidence

- 2026-09-24 process sweep: 70 orphaned `Python314\python.exe -c "from multiprocessing.spawn import spawn_main; spawn_main(parent_pid=…)"` workers, all with dead parents. They came in two batches: 46 at 15:05, when Claude session PID 32400 started with 2 parents, and 24 at 22:40, when session PID 32456 started with 2 parents. They were killed manually. The per-parent counts (~23 or 12 each) match a 24-CPU default pool.
- The repo's own `src/` has no direct `multiprocessing` use. The only pool on the startup path is Rope's `generate_cache`.
