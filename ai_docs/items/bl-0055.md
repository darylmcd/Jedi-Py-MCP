# bl-0055 — Worktree files resolve to the enclosing primary checkout's workspace

**row:** `bl-0055` · **pri:** `High` · **size:** `S`

## Anchors

- `src/python_refactor_mcp/workspace_registry.py:156-196`
- `tests/unit/test_workspace_registry.py`

## Acceptance

- [ ] `resolve_workspace_root` returns the deepest directory carrying a project marker (any entry of `_PROJECT_MARKERS`: a `.git` file or dir, a pyproject, setup.py or setup.cfg marker) whenever that directory is deeper than every matching known root; a known root wins only when no deeper marker exists.
- [ ] The marker walk includes the path itself when it is a directory; a file path still starts at its parent. Today the walk starts at `resolved.parents` (`workspace_registry.py:183`), so a directory argument such as `root_path` never counts as its own root.
- [ ] Red-first unit tests in the anchored test file, each failing at HEAD `f2d6074` and passing after: (a) a known root directory with a pyproject marker, plus a nested worktree under its `.worktrees/x/` holding a `.git` file and its own pyproject marker; resolving a module inside the worktree returns the worktree root. (b) Resolving the worktree root directory itself returns the worktree root, both with no known roots and with the primary registered as a known root. (c) Resolving an unregistered repo root directory returns that directory instead of raising `WorkspaceResolutionError`.
- [ ] The resolved worktree root is auto-registered like any discovered root; a second call returns the same root without resolving to the primary.
- [ ] Existing nested-workspace and known-root tests in the anchored test file stay green unmodified.

## Evidence

- `workspace_registry.py:166-180` returns the longest known-root prefix before the marker walk at `:182-190` runs, so any path inside a known root wins even when a deeper `.git`/`pyproject.toml` exists. Files under `<primary>/.worktrees/<x>/` therefore resolve to the primary checkout, and Pyright answers from the primary program (`include: ["src/"]`), not the worktree being edited.
- The walk at `:183` iterates `resolved.parents`, which excludes the path itself. A probe of a real `WorkspaceRegistry` at `f2d6074` (cold review, 2026-09-28): with no known roots, `resolve_workspace_root(<primary>/.worktrees/x)` returned `<primary>` and `resolve_workspace_root(<unregistered repo root>)` raised `WorkspaceResolutionError`; with the primary known, both the worktree root and a module inside it returned `<primary>`. `get_workspace_diagnostics(root_path=...)` already routes a directory through this walk, and the CLI pre-warm (`server.py:81`) and path-less fallback (`tool_runtime.py:172`) work around it with synthetic child paths (`__init__.py`, `__fallback__`).
- The known root arrives through the CLI pre-warm (`server.py:80-83`) or through auto-registration (`:187-188`) the first time any primary-checkout file resolves, so removing the pre-warm alone does not fix this.
- Source: 2026-09-27 15-day session retrospective, canonical issue `jedi-workspace-root-misresolution` (3 sessions). Confirmed by code reading at HEAD `f2d6074` and by the directory-argument probe above.
