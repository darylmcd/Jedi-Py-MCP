# bl-0055 — Worktree files resolve to the enclosing primary checkout's workspace

**row:** `bl-0055` · **pri:** `High` · **size:** `S`

## Anchors

- `src/python_refactor_mcp/workspace_registry.py:156-196`
- `tests/unit/test_workspace_registry.py`

## Acceptance

- [ ] `resolve_workspace_root` returns the deepest ancestor carrying a project marker (any entry of `_PROJECT_MARKERS`: a `.git` file or dir, a pyproject, setup.py or setup.cfg marker) whenever that ancestor is deeper than every matching known root; a known root wins only when no deeper marker exists.
- [ ] Red-first unit test in the anchored test file: a known root directory with a pyproject marker, plus a nested worktree directory under its `.worktrees/x/` holding a `.git` file and its own pyproject marker; resolving a module inside the worktree returns the worktree root. Fails at HEAD `f2d6074`, passes after.
- [ ] The resolved worktree root is auto-registered like any discovered root; a second call returns the same root without resolving to the primary.
- [ ] Existing nested-workspace and known-root tests in the anchored test file stay green unmodified.

## Evidence

- `workspace_registry.py:166-180` returns the longest known-root prefix before the marker walk at `:182-190` runs, so any path inside a known root wins even when a deeper `.git`/`pyproject.toml` exists. Files under `<primary>/.worktrees/<x>/` therefore resolve to the primary checkout, and Pyright answers from the primary program (`include: ["src/"]`), not the worktree being edited.
- The known root arrives through the CLI pre-warm (`server.py:80-83`) or through auto-registration (`:187-188`) the first time any primary-checkout file resolves, so removing the pre-warm alone does not fix this.
- Source: 2026-09-27 15-day session retrospective, canonical issue `jedi-workspace-root-misresolution` (3 sessions). Confirmed by code reading at HEAD `f2d6074`; not reproduced live.

## Context

- High: it blocks safe use of the Python MCP tools by worktree-based agents (`/backlog-remediate` executors edit in `<repo>/.worktrees/<id>/`).
- Sibling shape from the same retro issue: path-less tools fall back to the most-recent or pre-warmed workspace → `bl-0056`. Independent fix; no ordering dependency.

## Notes

- Decide deliberately between "deepest marker of any kind" and "deepest `.git` boundary first, then other markers". A fixture sub-project with its own `pyproject.toml` inside a known root changes behavior under the first rule (it becomes its own workspace and spawns its own Pyright). Pin the chosen behavior with a test either way.
